# Улучшение качества Tesseract-fallback: что попробовано, что не помогло

Дата: 2026-09-21. Продолжение `OCR_FALLBACK_HARDENING_REPORT.md`, которое закрыло
инфраструктурные дефекты (тихий отказ, CMap-детектор, PUA-таблица) и честно измерило
`ocr_character_accuracy` на Tesseract-фоллбэке: **0.7761** (n=71, `evaluation/silver_labels/
ocr_gold_review_pass1.jsonl`, строки с `source_provenance=TESSERACT_RUS_ENG_PREANNOTATION`)
— ниже порога ТЗ 14.3 (≥0.95), в отличие от `PDF_TEXT_LAYER`-пути (0.9576, порог пройден).

**Итог этого прохода: ни одно из протестированных изменений не дало значимого честного
улучшения `ocr_character_accuracy` на Tesseract-подмножестве. Продовый код (`api_service/
app/domain/dataset_sources.py`, `api_service/app/config.py`) не изменён — все эксперименты
были явно хуже базовой линии или статистически неотличимы от неё (перекрывающиеся 95%
Wilson-интервалы), поэтому ни один не был принят** (правило сессии: оставлять только то,
что реально помогает, не подгонять метрику под ожидание).

Все измерения — **внутри Docker-образа** (`lct-hack-2026-api:latest`, tesseract 5.5.0,
`rus.traineddata`/`eng.traineddata` из `tesseract-ocr-rus=1:4.1.0-2`); локальный tesseract
на этой машине сломан (tesseract 3.02) и вне области работ (общая машина). Каждый шаг
измерялся отдельно, по одному изменённому параметру за раз; между шагами код откатывался
к подтверждённой базовой линии перед следующим экспериментом.

Вспомогательное изменение инструмента измерения (оставлено, не относится к самому
tesseract): `evaluation/ocr_fixtures.py` теперь умеет выводить `metrics_by_source_provenance`
— разбивку `ocr_character_accuracy`/`ocr_wer`/`ocr_coverage` отдельно по `PDF_TEXT_LAYER` и
`TESSERACT_RUS_ENG_PREANNOTATION`, а не только общую цифру по всем 223 строкам. Без этого
нельзя было измерить эффект изменения, ограниченного OCR-фоллбэк-путём, не разбавляя сигнал
152 строками текстового слоя, которые эти изменения не затрагивают.

## 1. Препроцессинг изображения (бинаризация, апскейл)

**Гипотеза, которая не подтвердилась.** Ожидалось, что мелкий текст на крупноформатных
листах (штампы/размерные надписи) рендерится при слишком низком эффективном DPI. Диагностика
подтвердила часть гипотезы: 58 из 71 строк (82%) лежат на страницах A4-формата (595×842pt),
и текущий рендер там упирается в `_OCR_PAGE_ZOOM_MAX=3.0` (≈216 DPI), тогда как встроенное
растровое изображение внутри PDF — реально ~300 DPI (3508×2480px). То есть страница рендерится
для OCR **ниже** собственного разрешения скана.

Тем не менее, поднятие эффективного разрешения (шаги 2 и 3) **последовательно ухудшало**
и точность, и `ocr_coverage` (долю golden-строк, для которых вообще нашлось хоть одно
совпавшее OCR-слово в пределах допуска bbox-сопоставления в `ocr_fixtures.py`). Ухудшение
не связано с таймаутами (проверено по логам контейнера — ни одного
`nonzero_exit`/`invocation_failed`/таймаута ни на одном из шагов). Вероятная причина:
`--psm 11` («sparse text», без модели полной вёрстки страницы) на более высоком разрешении
резолвит больше мелких артефактов чертежа (штриховка, тонкие рамки таблиц, сглаживание
шрифта) как отдельные текстоподобные блоки — это фрагментирует реальные слова на бОльшее
число мелких bbox с сдвинутыми центрами, из-за чего они чаще выпадают из узкого допуска
сопоставления (`y_slack=3pt`, `x_slack=5pt`) вокруг золотой bbox-строки. Наблюдаемое падение
`ocr_coverage` (0.761→0.690 на шаге 3) это подтверждает.

Otsu-бинаризация (шаг 1, чистый Python без новых зависимостей — `_otsu_threshold`/
`_binarize_for_ocr` в `dataset_sources.py`, откачено) также ухудшила результат: глобальный
порог на всю страницу, вероятно, стирает тонкие/сглаженные штрихи текста на части
чертёжных страниц, где нет чистого чёрного-по-белому скана.

**Деskew (наклон) не тестировался отдельно** — учитывая, что оба более простых
преобразования (бинаризация, апскейл) последовательно ухудшали результат на этом
конвейере (`--psm 11`, полностраничный рендер), а основной документированный источник
геометрических искажений в этом корпусе — не наклон скана, а явный `/Rotate`-флаг
страницы (см. раздел 3) — приоритет сместился на проверку последнего вместо слепого
добавления ещё одного глобального преобразования той же природы.

## 2. Подбор `--psm`

Замерены `--psm 3` (полный автоматический анализ вёрстки), `4` (одна колонка текста
переменного размера), `6` (единый однородный блок текста), `12` (`sparse text` + OSD) —
против текущего продового `--psm 11` (`sparse text`, без OSD). Изменение сделано только
в `_run_tesseract_tsv` (полностраничный фоллбэк — единственный путь, покрытый этой
gold-выборкой); точечный OCR-путь (`_ocr_original_clip`, кропы) не трогался — для него нет
отдельной eval-выборки, менять вслепую было бы неоправданно.

`3`/`4`/`6` — заметно хуже как по точности, так и по `ocr_coverage`: эти режимы
предполагают вёрстку связным текстовым блоком/колонкой, а реальный контент — разрозненные
фрагменты (штампы, размерные надписи, примечания) на чертёжном листе, что и предполагает
`sparse text`. `12` статистически неотличим от `11` (текущего). **Вывод: текущий выбор
`--psm 11` уже соответствует характеру контента этого корпуса — не улучшен, а
подтверждён.**

## 3. Russian LSTM traineddata: используется ли legacy-движок

Проверено эмпирически внутри Docker-образа (не по предположению):

```
$ tesseract probe.png stdout -l rus --oem 0 --psm 11   # только legacy-движок
Error: Tesseract (legacy) engine requested, but components are not present
       in /usr/share/tesseract-ocr/5/tessdata/rus.traineddata!!
Failed loading language 'rus'

$ tesseract probe.png stdout -l rus --oem 1 --psm 11   # только LSTM
те123
$ tesseract probe.png stdout -l rus --oem 3 --psm 11   # default (auto)
те123    # идентичный результат
```

`--oem 0` падает — в пакете `tesseract-ocr-rus=1:4.1.0-2` **нет данных legacy-движка
вообще**, только LSTM. `--oem 1` и `--oem 3` (текущий продовый вызов не передаёт `--oem`,
то есть использует default=3) дают идентичный результат. **Вывод: продовый код уже
использует исключительно LSTM-движок — заявленный в задаче риск не подтвердился, менять
нечего.**

Побочно обнаружено: `rus.traineddata`/`eng.traineddata` из этого Debian-пакета — это
«fast»-вариант (integer-квантованные веса, 3.86MB/4.11MB), а не более точный «best»/
standard вариант (float-веса, ~15MB на язык). Это стандартная политика Debian-пакетов
`tesseract-ocr-*` (компактность vs точность) — не входит буквально в вопрос
«legacy vs LSTM» задачи, но напрямую влияет на точность распознавания, поэтому
проверено как естественное продолжение того же пункта (см. ниже).

### tessdata_best вместо tessdata_fast

Скачаны `rus.traineddata`/`eng.traineddata`/`osd.traineddata` из
`github.com/tesseract-ocr/tessdata_best` и примонтированы поверх штатных файлов внутри
контейнера **на уровне отдельных файлов** (не всей директории `tessdata/` — первая попытка
подменить всю директорию случайно затёрла системную поддиректорию `tessdata/configs/` пакета
`tesseract-ocr`, из-за чего флаг `tsv` переставал резолвиться и `_run_tesseract_tsv` тихо
возвращал пустой результат — `ocr_character_accuracy` обрушился до артефактных 0.0062/
`coverage` 0.014, то есть в точности воспроизвёл паттерн «сломанного окружения» из прохода 1;
это баг тестовой обвязки, а не находка про `tessdata_best`, и он был найден и исправлен
до того, как попасть в итоговую таблицу).

После исправления монтирования: **0.7812** [0.754, 0.806] против базовых **0.7761**
[0.749, 0.801] — доверительные интервалы почти полностью перекрываются, разница
статистически незначима при n=71. Побочная цена: единичный вызов `tesseract` на реальной
странице корпуса занял **7.7 секунды** против кратно меньшего времени со штатной моделью
(не измерено точно, но с 4x большим по объёму файлом модели загрузка сети заметно
доминирует над самим распознаванием на этих небольших изображениях), плюс +4 к размеру
образа на диске (~34MB → ~34+27MB). **Вывод: не принято** — прирост в пределах шума, цена
(латентность, размер образа) реальна и не оправдана для этого выигрыша.

## 4. Проверенная и отклонённая гипотеза: рендер повёрнутых (`/Rotate`) страниц

Диагностика (см. `diag_rotation_correlation.py` в этой директории) показала: **44 из 71
строк (62%) лежат на страницах с `/Rotate 270`**, и на этих строках точность заметно ниже
(0.7616, n=537 симв.), чем на неповёрнутых (0.8657, n=432 симв.) — на неизменённом,
текущем продовом коде. Ожидаемая по прошлым чекпоинтам (`[[project_case10_rotation_fix]]`)
гипотеза: полностраничный OCR-рендер (`_ocr_page_words`, `page.get_pixmap(matrix=
fitz.Matrix(zoom,zoom))`, без учёта `page.rotation_matrix`) рендерит страницу в «сыром»,
неповёрнутом виде, тогда как bbox золотой разметки — в «видимой» (после `/Rotate`) системе
координат, как это уже было исправлено для пути текстового слоя.

**Гипотеза проверена и опровергнута прямым визуальным сравнением, а не оставлена как
предположение.** Отрендерены оба варианта одной и той же повёрнутой (`/Rotate 270`)
страницы: текущий код (без `page.rotation_matrix`) — текст выходит **прямым, читаемым**;
версия с явным умножением на `page.rotation_matrix` — текст выходит **повёрнутым набок**
(двойное применение поворота). То есть **текущий рендер уже корректен**, дополнительная
правка была бы регрессией, а не фиксом — этот путь закрыт, изменений не внесено.

Тогда почему разница в точности всё равно есть (0.76 vs 0.87)? На выборке худших
повёрнутых строк (`worst_rotated_lines.txt`) видно, что заметная часть — короткие golden-
строки (4–7 символов, иногда 0 — размеченные ревьюером как пустые), где: (a) OCR находит
соседний/более широкий фрагмент текста, чем узкая golden-bbox (напр. gold `"2022;"` vs
предсказано `"07.06.2022;"` — предсказание не ошибочно, просто шире), либо (b) в пустых
golden-строках сопоставление по bbox-допуску подхватывает случайный близлежащий штрих/
символ печати. Это похоже на шум **метода измерения на коротких фрагментах**, а не на
дефект распознавания текста как такового — предположительно эти страницы (сертификаты
соответствия, печати) статистически чаще имеют этот `/Rotate`-флаг, чем чертёжные листы,
и одновременно чаще имеют плотные короткие аннотации у печатей, а не что связь причинная.
Дальнейшее расследование (например, отдельная метрика без строк с `gold_len < N`) не
проводилось — не входит в объём этого прохода, задокументировано как открытый вопрос.

## 5. Альтернативный OCR-движок — trade-off (не реализовано, по заданию)

Поскольку последовательные попытки (препроцессинг, `--psm`, лучшие веса LSTM) не дали
значимого прироста, вероятный потолок для Tesseract 5 на этом типе контента (мелкий текст
в штампах/размерных надписях на инженерных чертежах, часто на серых/текстурированных
сканах) уже близко достигнут в текущей конфигурации. Ниже — варианты, **не внедрённые**,
для дальнейшего рассмотрения:

| Движок | Плюсы | Минусы / риски |
|---|---|---|
| **PaddleOCR** (PP-OCRv4, open-source) | Обычно заметно точнее Tesseract на «диком» контенте (шум, мелкий текст, нестандартная вёрстка); есть готовая русская модель | Новая тяжёлая зависимость (PyTorch/PaddlePaddle-эквивалент), заметно больше образ, требует отдельного цикла валидации на этом же gold-наборе, лицензия Apache-2.0 (ок) |
| **EasyOCR** | Проще PaddleOCR в интеграции, PyTorch-based | Обычно медленнее и не всегда точнее Tesseract на плотных инженерных чертежах по опыту сообщества; тоже новая тяжёлая зависимость |
| **docTR** (Mindee) | Современная detection+recognition архитектура, активно поддерживается | Тяжёлая зависимость (TensorFlow или PyTorch), нет готовой русской модели «из коробки» такого же качества, как eng |
| **Yandex Vision OCR / Google Cloud Vision** (облачный API) | Обычно наивысшая точность на кириллице «из коробки», не требует локальных ML-зависимостей в образе | **Сетевая зависимость и стоимость за вызов** — неприемлемо для оффлайн/воспроизводимого пайплайна оценки этого кейса (текущая архитектура — self-hosted, без внешних API на пути инференса); также требует передачи содержимого документов во внешний сервис — вопрос конфиденциальности данных исходников |

**Рекомендация (не реализована):** если потребуется дальнейшее повышение
`ocr_character_accuracy` выше текущих ~0.78, следующий кандидат для пилота — PaddleOCR
(offline, есть русская модель, активное сообщество для инженерных/сканированных
документов) — но это отдельная, более крупная по объёму задача (новая зависимость,
сборка образа, повторная валидация на этом же gold-наборе), не входящая в рамки этого
прохода point-tuning'а существующего Tesseract-вызова.

## Итог

`ocr_character_accuracy` на Tesseract-фоллбэке остаётся **0.7761** (n=71) — ниже порога
ТЗ 14.3 (≥0.95), как и было до этого прохода. Пять направлений проверены и отклонены как
не дающие честного улучшения (см. таблицу); два пункта задания (LSTM-движок, `--psm`)
закрыты как **подтверждение уже корректной конфигурации**, а не как правка. Единственная
оставленная в коде правка — разбивка метрик по `source_provenance` в
`evaluation/ocr_fixtures.py` (инструмент измерения, не сам OCR).
