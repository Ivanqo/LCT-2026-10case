### 1.1. Поля 1.1 в выгрузке

Каждая проверка дополнительно к полям `submission_schema.json` несёт: `object_id`, `parameter_id`,
`parameter_code_legacy`, `matrix_code`, `rule_version`, `evidence_group_id` (хэш: объект + код + location + набор
цитат), `finding_id` (хэш: объект + код + location — стабилен при смене доказательств), `expected_value` /
`actual_value` (+ `expected_stage` / `actual_stage`), `source_expected_*` и `source_actual_*` (file_id, sha256, stage,
code, revision, approval, page, bbox_polygon), `approved_change_ref = "NONE"`, `completeness_status`, `finding_status`,
`finding_status_internal`, `review_priority`, `confidence`, `dataset_version`, `matrix_version`, `model_version`,
`input_manifest_hash`. Каждое доказательство: `page`, `sha256`, `document_code`, `revision`, `approval_status`,
`bbox_norm` ([x0, y0, x1, y1] в [0;1], начало — левый верхний угол), `coordinate_space`, `role`. На верхнем уровне —
`export_conventions` (стиль кода, версия таблицы, формат bbox, версии, хэш манифеста).

Решения, которые стоит знать:
- `finding_status` в схеме GOLD — только NEGATIVE_VERIFIED / CANDIDATE / CONFIRMED_VIOLATION / SUSPICION. Наши
  воздержания (MISSING_EVIDENCE, NOT_APPLICABLE, NOT_COMPARABLE, CLARIFICATION_REQUIRED, LOW_QUALITY) выражаются через
  `completeness_status`, а `finding_status = null`; внутренний статус — в `finding_status_internal`.
- `expected_value` — значение первой стадии по порядку ПД → РД → ИД (ПД — эталон), `actual_value` — следующей.
- bbox в пикселях/пунктах нормализуется по размеру страницы, если он известен; иначе `null` (не угадываем).
- Инструменты стенда, которые сопоставляют проверки по внутреннему коду (`seed_l1`, `metric3`, `compare_runs`), запрашивают
  `code_style="legacy"`. Сравнение выгрузок до и после P0 побайтно не совпадёт — это изменение формата, не поведения.

## 2. Как считает grader_sim (наше прочтение листа «МЕТРИКИ»)

- **Единица** — evidence group. Прогноз положительный, если `violation_label = VIOLATION_PRESENT`.
- **Варианты совпадения**: `key_only` (объект + код + location STRICT; диагностика), **`evidence_page`** (основной: + для
  каждой стадии эталона процитирована одна из его пар file+страница), `evidence_page_loose_location` («012» ~ «12»,
  вложение названий элементов), `evidence_strict` (+ IoU ≥ 0,50 с прямоугольником эталона; строки без прямоугольников
  исключаются и считаются отдельно). Коды сравниваются в любой конвенции через таблицу 1.1; FREE-* — буквально.
- **Precision** в двух вариантах, т.к. плотность разметки скрытого теста неизвестна: *закрытая* — FP только на
  размеченных ключах (ключ отрицательной строки или ключ/страницы положительной с неверным кодом/доказательством);
  *открытая* — любой положительный прогноз на объектах набора, не ставший TP.
- **FPR** = отрицательные, на ключ (для пар страниц — на страницы) которых пришёлся положительный прогноз / все
  отрицательные. «Устаревшие редакции» из листа «МЕТРИКИ» не размечены — не измеряется. Рядом — доля отрицательных,
  подтверждённых вердиктом `NO_VIOLATION` (иначе FPR = 0 достигается воздержанием).
- **Полнота локализации** — среди найденных на уровне ключа положительных: доля с верными file+страница и с IoU ≥ 0,5.
- **Связка документов** — цитаты проверок с вердиктом: файл принадлежит объекту по реестру и стадия совпадает; шифр и
  редакция — только где их знает реестр (сейчас нигде).
- **Миры** (`world`): посевы D оцениваются каждый в своём прогоне (прогноз одного случая не засчитывается другому).

  недоступен — как и в прогонах стенда A. В Docker-образе Tesseract 5.5; цифры на сканах там могут быть другими.
- Выборки крошечные (19 / 9 в A), SILVER — один аннотатор; интервалы в таблицах широкие — сравнивать изменения по k/n.

  нашим `bbox_norm` (`SOURCE_PAGE`) для повёрнутых страниц не проверено — строгий вариант на них пока условен.
- FPR на устаревших редакциях не измерим (нет меток); шифр/редакция в связке не проверяемы (нет реестра 1.1).
- Посевы — только L1 (L2 в стенде A совпал с L1 в 24/24 случаях).
