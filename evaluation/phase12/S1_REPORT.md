## 2. Как работает

1. **Документы**: ПД и РД с тегом раздела «АР» (`document_facts`), без исключённых/заменённых (`GateContext`).
   Текстовый префильтр по всем страницам (`экспликац|спецификац|ведомост … помещ|квартир`), затем разбор кандидатных
   страниц через `dataset_sources.extract_original_pages` (тот же кадр координат с учётом Rotate, что и везде).
   Страницы с битой картой шрифта (`cmap_corruption_suspected`) и таблицы с «кашей» Latin-Extended/PUA → в
   `diagnostics.low_quality`, не сравниваются.
2. **Пары таблиц**: одинаковый вид (помещения/квартиры), совместимый охват (этаж / секция / корпус / МОП, БКТ,
   квартиры — из заголовка, иначе из единственной подписи «План … этажа» на листе), ≥2 общих ключа и ≥50 % пересечения;
   балл = пересечение + Жаккар + согласие имён + согласие площадей + бонус за известный этаж, порог 1,7.
   - **ПД — эталон, самая новая редакция** по маркерам (папка-поколение, «Изм.N», дата) среди кандидатов в пределах
     0,8 от лучшего балла; неупорядочиваемые редакции с тем же рангом → «робастная» проверка: расхождение
     сообщается, только если оно есть против каждой такой редакции (`CASE10_EXPLICATION_REVISION_POLICY=robust|block`).
   - **РД**: каждый том сравнивается; из изданий одного тома (одинаковый ключ раздела, напр. «АР1» и «АР1_Изм3») —
     только новейшее (устаревшая редакция не цитируется); одинаковая таблица на нескольких листах одного файла —
     одно сравнение, остальные листы цитируются как копии; разные таблицы одного тома за одну таблицу ПД — только
     наиболее похожая.
3. **Строки**: по номеру (нормализация «Ст.1.1.1»≈«1.1.1», «012»≈«12»), запасные ключи — уникальное одинаковое имя,
   затем уникальная пара (имя, площадь). Имя равно после нормализации, при вложении (перенос/уточнение) или опечатке
   (сходство ≥ 0,8). Площадь отличается, если |Δ| > max(1 % от ПД, 1 единица печатной точности) по ближайшей паре
   значений ячейки (в ячейке бывает два числа — исправленное рядом с зачёркнутым). «Есть только в одной стадии»
   сообщается, если таких строк мало (≤3 или ≤25 %) и таблицы соизмеримы — иначе это выноска/фрагмент листа;
   целиком отсутствующая квартира покомнатно не сообщается.
4. **Выход**: одна evidence_group на расхождение, `location` = номер как на листе ПД (для добавленного — РД),
   `delta.finding_group` = пара таблиц (файл:лист ПД | файл:лист РД | этаж); одна группа M-002 на итог этажа
   (VIOLATION только при > 1 %); одна NEGATIVE_VERIFIED группа на пару таблиц без расхождений. Доказательства:
   строка ПД (`expected`) и РД (`actual`) + bbox таблицы каждой стадии (`table`) + зона изменённых строк
   (`zone`, ≥2 строк) + копии листов. Роль `table`/`zone` сортируется после `expected`/`actual`, поэтому
   `pd_value/rd_value` экспорта — значения строки. Confidence 0,8 (по номеру) / 0,6 (запасной ключ) / 0,7
   (только в одной стадии), −0,1 при конфликте редакций, −0,1 если этаж не известен с обеих сторон.

## 4. Не покрыто / ограничения

- **Порог ≥3 официальных кейсов недостижим по данным**: на диске два объекта с gold-кейсами по экспликациям.
- ТЭП покрыт частично: словари M-001, M-002, M-004, M-005, M-006, M-008 и M-010 имеют provenance только из
  ALT79B/LOS3A; для остальных M-003, M-007, M-009, M-011, M-012, M-019/020, M-024…028 не добавлялись неподтверждённые варианты.
  Числовой generic-extractor выдаёт только `CANDIDATE`; полноценной gold-разметки ТЭП для оценки precision нет.
- LOW_QUALITY комнатных таблиц S1 остаётся в diagnostics аудита `EXPLICATION_COMPARE`; связи с S3 LOW_QUALITY
  evidence-group пока нет, потому что S1 table diagnostics не несёт source-fragment id и формируется после
  матричного цикла групп.
- POL16-тип (площади квартир в штампах на плане) осуществим отдельным парсером штампов и matcher по номеру/
  типу квартиры между планами ПД/РД; текущий table-row parser не покрывает этот источник. Оценка без привязки
  к конкретному объекту; реализация не сделана.
- Посевы — только L1 (лексические мутации слов одного листа), без мутации заголовков и охвата.
- Холодный live-tagger кэш может инвалидироваться общим отпечатком `dataset_sources.py` после S3-изменений;
  DOO25 control run занял 2083,3 с, хотя отдельный S1-скан укладывается в 11,53 с. Нужен прогрев tagger-кэша
  после слияния изменений S3/S1 перед оценкой задержки всего run_process.
