# S2 — ОВ-планы, комнатные сравнения и якоря

Дата: 2026-09-28

## Изменения

- Добавлена классификация страниц по заголовкам/штампу и текстовым признакам планов ОВ и отопления. Реестр `document_manifest.registry` используется как сигнал дисциплины, метаданные организатора — только для ранжирования поиска.
- Добавлены точные напечатанные номера помещений, нормализация П2/ВЕ/В2.4…В2.10/В3.1 и сравнение систем ПД → РД. Зоны помещений строятся один раз на лист; OCR локального фрагмента вызывается только когда текстовый слой не дал систему.
- Проход страниц ограничивает слабые совпадения «числа + метки систем»: в проверочном текстовом проходе TYU из 79 страниц с ОВ-признаками в ПД оставлены 36 (включая все 24 страницы с явными заголовками); всего детальная выборка сократилась со 108 до 67 страниц. Это локальная проверка отбора, не замер полного конвейера.
- Удалены `_is_100_room`/`_is_300_room`, выбор по `РД-ОВ1`, проверка `dataset_section == OV`/`RD_ID_MIXED` и требование `MATRIX_FIELD`.
- KR-055/KR-058/PZ-009 используют `anchor_vocab`; названия бетонных/фундаментных элементов извлекаются из исходного текста, а не из названий Новослободской.

## Проверки

- `py_compile` для трёх доменных модулей — успешно.
- `test_case10_official.py` и `test_case10_p0_conventions.py` — 36/36 успешно.
- Точечный harness на фиксированных листах TYU (F0171 p.88/p.104, F0201 p.17/p.18/p.20) получил rule-кандидаты во всех 6 целевых местах: M-078 140/142/147/198/314 и M-079 012. В комнате 314 ожидаемые V3.1/V3.2 ПД сравниваются с РД; фактическая привязка РД V3 к комнате пока остаётся слабой. Также появились два неразмеченных кандидата M-078 — комнаты 323 и 341; без полного A/B их нельзя подтвердить или назвать FP. Harness не заменяет live-прогон и не доказывает полноту локализации.
- Точечный проход сравнения этих листов занял 13,0 с для IOS4-078 и 2,1 с для IOS4-079; это только пятистраничный microbench, не время на объект.
- Выполнен текстовый discovery TYU: 602 страницы проверены по содержимому, 67 страниц оставлены для геометрии. Страницы ПД 88/104 и РД 17/18/20 входят в эту выборку.
- Проверены отсутствие перечисленных выше хардкодов и `git diff --check` на S2-файлах — совпадений/ошибок нет.
- Полные `run_baseline.py --mode live` с включённым сравнением (два запуска) не завершились за 10 минут каждый и были остановлены без протокола. Контроли с флагом `CASE10_ROOM_DRAWING_COMPARE_ENABLED=0` также не завершились: один остановлен после >10 минут, второй — после >5 минут. Поэтому эти запуски не дают ни B, ни корректного текущего замера добавочного времени. На общей машине параллельно шёл S1-прогон; старый baseline 48,0 с снят на другом слепке/тёплом кэше и не сравним с этими холодными запусками.

## Открытые пункты приёмки

- A (организатор TYU/NOV), B (живой TYU), C (посев L1 другого объекта с ≥20 нетронутыми комнатами) и критерий времени не приняты: завершённых выгрузок нет.
- В PDF ПД визуально есть контуры тёплого пола в комнатах 267/270/271/272 (F0171, PDF p.99); соответствующая страница РД — F0202, PDF p.17. Автоматический текстовый детектор дал 0 комнат и не создал `FREE_SEARCH`; ручной осмотр не считается машинной находкой.
- Предыдущий синтетический snapshot-тест L1 (10/10) не является валидной проверкой на другом объекте; среди выбранных номеров были вероятные размеры/обозначения, поэтому recall/FP не засчитываю.
- `CASE10_ROOM_DRAWING_COMPARE_ENABLED` оставлен выключенным по умолчанию: B и бюджет +60 с не подтверждены. Для изолированного вызова флаг `1` включает discovery/сравнение по листам.

## Итог

Реализованы универсальные classifier и комнатный extractor; на известных страницах TYU точечный извлекатель восстановил 6/6 мест и обработал особый случай комнаты 314. Полная приёмка не достигнута: живой процесс и контроль не завершились, скорость и регрессия A не измерены, контуры тёплого пола автоматически не найдены, посевы L1 не проверены. Флаг остаётся выключенным; необходима интеграционная оптимизация/замер на тёплом кэше до включения по умолчанию.
