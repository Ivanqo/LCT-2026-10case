## 2. Серверный пакетный путь (пункт 3)

`app/batch_package.py` — общий код CLI и HTTP:

- **Пакет**: папка или ZIP. ZIP распаковывается один раз в каталог по его SHA-256; защита от zip-slip (абсолютные
  пути, `..`, буквы дисков, симлинки отбрасываются), имена cp866 без флага UTF-8 читаются правильно, предохранитель
  от ZIP-бомбы `CASE10_BATCH_MAX_UNPACKED_BYTES` (256 ГБ — это не лимит пакета). Обход файлов сортирован (не порядок
  файловой системы), у каждого файла SHA-256.
- **Реестр** (Перечень ИД 1.1): CSV (`,`/`;`/таб, UTF-8 или cp1251), XLSX (без сторонних библиотек), JSON/JSONL;
  синонимы заголовков (`SHA-256`, `Стадия`, `Шифр`…), нормализация стадий, статусов, дат (включая серийные даты
  Excel). Сопоставление файла со строкой — по SHA-256, затем по пути, затем по уникальному имени.
- **Статус пакета**: без реестра — `CLARIFICATION_REQUIRED/REGISTRY_MISSING`; файл вне реестра, другой SHA-256,
  повтор `file_id` — `CLARIFICATION_REQUIRED/REGISTRY_DOES_NOT_MATCH_PACKAGE` с перечнем; строки реестра без файла
  перечислены. Стадия — из реестра, иначе из имён папок пакета тем же правилом, что живой режим P0; папка, в которую
  положили пакет, стадию не решает. `file_id` — из реестра, иначе `F-` + 16 знаков SHA-256.
- **Импорт** — тем же путём, что официальный датасет (`_import_document_manifest`), плюс поля реестра, которых там
  нет: шифр, редакция, дата утверждения, цепочка predecessor/successor. Что делать со статусами реестра (выбор
  редакции, блокировка вывода) — решает слой решений S3; реестр сохранён у каждого документа в
  `dataset_metadata.document_manifest.registry`.

**CLI** `python -m app.cli run|validate` (`app/cli.py`): процесс целиком в одном интерпретаторе, без очереди и
кэш-сервера; результат = `protocol_to_submission` + блок `package`; перед записью — проверка
`submission_schema.json` и базовая проверка формата, код выхода 2 при нарушении. В `result.json` нет времени, путей
и id базы — повторяемый SHA-256. Отдельно `--timings`: исключительное время стадий, пик RSS дерева процессов и
cgroup, пик VRAM, покрытие тэггера.

**HTTP** `POST /api/case10/batch-runs` (роль ADMIN/SUPERVISOR): путь к пакету и реестру относительно
`CASE10_BATCH_PACKAGES_ROOT` (другие пути — 422/404), импорт в базу сервиса, процесс в очередь воркеру; процесс
виден в интерфейсе инспектора. `GET …/{process_id}` — состояние и отчёт о пакете, `GET …/{process_id}/result` — JSON
в формате CLI. S5 открыл эти маршруты в шлюзе (`5338dde`). В `docker-compose.case10.yml` переменные
`CASE10_BATCH_PACKAGES_ROOT` и `CASE10_ORIGINALS_ROOT` заданы как `/data/packages` для API и воркера.

**Стендовый smoke-прогон 27.09.2026:** `packages/s6-smoke` содержит три синтетических одностраничных PDF (PD/RD/ID),
реестр `packages/s6-smoke.registry.json`; `POST /api/case10/batch-runs` импортировал все 3 файла со статусом
`ACCEPTED`, без проблем. Процесс `754cc179dce4471ab3f2aa0a6c226157` перешёл в `READY`;
`GET …/{process_id}/result` вернул результат, проверенный сервером по `submission_schema.json`, сохранён в
`packages/result.json` (251 341 Б, SHA-256 `7cd7cbeb561aa2f7d1c777f27ef2b5219194433c10a37747bf952e6dab04a603`).
Стенд доступен на `http://127.0.0.1:3100`, вход `admin` прошёл; снимок главной страницы снят через browser preview.

## 3. Лицензии (пункт 2)

`LICENSES_MODELS.md`. Кратко: MiniLM-L12 (Apache-2.0, 449 МБ, FP32 — без квантования, потому что запас до порога
0,45 измерен в FP32, а INT8 сдвигает оценки на ~10⁻²), Tesseract 5.5 с целочисленными моделями `tessdata_fast`
(Apache-2.0), Qwen3-4B — не в образе и выключен (BF16/NF4 по доле памяти GPU). Из библиотек внимания требует
**PyMuPDF (AGPL-3.0)**: для хакатона условие выполнено (код передаётся), для внедрения — коммерческая лицензия
Artifex или замена на pypdfium2. CUDA-библиотеки NVIDIA (2,8 ГБ) нужны только для GPU.

Хэширование здесь — 25–56 МБ/с: пакет читается через общий диск Docker Desktop (Windows → WSL2). На Linux-сервере с
локальным NVMe SHA-256 идёт со скоростью ≥ 0,5 ГБ/с на ядро. Извлечение значений и сравнение выполняются в
одном процессе и от числа ядер не ускоряются.

### 5.1 Найдено замером: OCR по таймауту и перегрузка потоков Tesseract

1. **Лимит по стенным часам в OCR.** `dataset_sources.py` вызывает Tesseract с `timeout=60` с на полностраничный OCR
   (строка 561) и `timeout=20` с на OCR фрагмента (387, 416). В холодных прогонах часть страниц не укладывалась в
   60 с (`ocr_page_tsv_invocation_failed … TimeoutExpired`): LOS3A — 7 страниц, DOO25 — 9 (в тёплом DOO25 — 13).
   Какие страницы получат текст, зависит от скорости и загрузки CPU. Это тот же класс недетерминизма, что E1 убрал
   из тэггера. Здесь обе пары прогонов совпали побайтно, то есть эти страницы не повлияли на вывод, но на быстрой
   машине они будут распознаны и могут повлиять. Кроме того, документ с такой страницей E1 намеренно не кладёт в
   кэш, поэтому тёплый прогон снова распознаёт его целиком: LOS3A — 2 документа, 344 с из 489.
   **Решение за I** (файл не мой, механизм OCR): заменить таймаут детерминированным ограничением — площадью
   растра в пикселях / DPI или числом OCR-страниц на документ. Таймаут оставить только как аварийный (например,
   600 с) с явным статусом страницы `LOW_QUALITY`/`NOT_COMPARABLE`.
2. **Перегрузка потоков.** Каждый процесс скана запускает Tesseract со своим пулом OpenMP (по умолчанию — по числу
   ядер хоста), и на квоте 3 CPU они мешают друг другу. В образе теперь задано `OMP_THREAD_LIMIT=1`: мой файл,
   на результат не влияет, E1 проверял побайтное совпадение слов и прямоугольников OCR при 1/2/без ограничения.
   Замер на LOS3A: скан 642 → 269 с, таймаутов 7 → 0, SHA-256 результата тот же (`e2ca4b79…`).
