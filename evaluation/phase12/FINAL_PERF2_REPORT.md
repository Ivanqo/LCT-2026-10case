## 6. Что нужно от других (шлюз, образ) — описано точными строками, файлы не правил

**gzip (`CASE10_API_GZIP=1`) через шлюз сейчас ломает ответ, поэтому по умолчанию выключен.** `node_gateway/server.js` берёт ответ API через `fetch` (undici сам разжимает тело) и копирует заголовки апстрима, кроме `hopByHopHeaders`; `content-length` там вырезается, а `content-encoding` — нет, так что клиент получает несжатое тело с `Content-Encoding: gzip`. Проверено локально: Python `gzip.decompress` на теле через шлюз → `BadGzipFile`. Исправление (проверено на копии `server.js`, тело 2,59 МБ → 0,14 МБ, JSON разбирается):

1. В `hopByHopHeaders` добавить `"content-encoding",`.
2. В `proxy()` перед `res.end(responseBody)` (и `const zlib = require("node:zlib");` вверху файла):
```js
let payload = responseBody;
if (payload.length >= 102400 && /gzip/.test(req.headers["accept-encoding"] || "") && /json/.test(upstreamResponse.headers.get("content-type") || "")) {
  payload = zlib.gzipSync(payload, { level: 4 });
  res.setHeader("Content-Encoding", "gzip");
  res.setHeader("Vary", "Accept-Encoding");
}
res.end(payload);
```
Тогда сжатие делает сам шлюз (прыжок API → шлюз внутри хоста сжимать не нужно, `CASE10_API_GZIP` оставить выключенным). На loopback gzip не ускоряет (p95 186 мс прямо и 239–241 мс через шлюз против 94 и 107 мс без сжатия), пользу даёт только по реальной сети.

**Образ/compose:** Dockerfile и compose менять не нужно — все новые кэши лежат под `CASE10_LIVE_TAGGER_CACHE_DIR=/data/live_tagger_cache` (подкаталоги `file_sha256/`, `embeddings/`, `ocr/`, `quality/` — каталог тома должен быть записываемым, в `hardened` это `/data`). Новые модули (`aux_pool.py`, `file_hash_cache.py`, `json_gzip.py`, `ocr_cache.py`, `quality_prefetch.py`) лежат в `api_service/app` и копируются целиком (`COPY api_service/app`, `!api_service/app` в `.dockerignore`, `api_service/app/**` в `make_delivery.py`). Поведение, которое меняется для Docker: пулы explication/free-hypotheses при `CASE10_LIVE_TAGGER_WORKERS=0` теперь параллельные (раньше серийные); отдельно вклад этого коммита не измерялся (в моих замерах `--workers 8` задан явно, т.е. серийный путь «0 = 1 воркер» не воспроизводился).

## 7. Что не измерено / ограничения (честно)

* Docker не пересобирался: «OKT103 >18 мин» в образе подтверждён только объяснением причины и результатом на хосте (то же 154-тысячное число размещений, тот же PyMuPDF 1.24.2 из `requirements`), прогон в образе нужно повторить после пересборки.
* Машина общая, тихих замеров нет; повторные холодные замеры одного кода различаются в 1,3–1,6 раза (см. v4/v5/v6 OKT103). Выводы устойчивы только по порядку величины и по load-независимой мере (CPU скана).
* Влияние монтирования Windows-каталога в Docker (в E1 `package_scan_sha256` 291 с и чтение ≈ 6 ГБ) на хосте не воспроизводится (нативный диск: 24–28 с); кэш SHA-256 убирает хеширование, но не первое чтение.
* Холодный прогон проверяющей стороны на новых данных выигрывает от п. 1, 6, 7, 9, 11 (это не кэши); кэши п. 2, 8, 10 работают на повторных прогонах и между воркерами и родителем.
* Кэш эмбеддингов привязан к конфигурации машины (число CPU, потоки torch); при переносе тома на другой хост ключ меняется и кэш пересчитывается, а не отдаёт «чужие» биты.
* OCR 23 страниц в родителе по-прежнему серийный на первом прогоне; параллельный OCR страниц правил не делал (страницы неизвестны заранее).
* Фронтенд не менялся: `npm run build` не запускался, формат ответа `protocols/current` (JSON, те же байты) не изменился.
* Не проверял `OMP_THREAD_LIMIT` + параллельный Tesseract отдельно.
* Падающие тесты в worktree, одинаковые на базе `f3568e4` и финале (данные организатора лежат вне репозитория): 8 — `test_case10_evaluation::…ocr_key_fields_null_with_reasons`, шесть в `test_case10_measurement_bench`, `test_case10_training_release::…hidden_labels…`.
