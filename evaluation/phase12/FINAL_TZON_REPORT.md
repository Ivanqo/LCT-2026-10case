## 1. Что меняется при включении

**Статусы `*_PARTIAL`.** Вход: те же файлы и реестр. Выход: поле `completeness` (`PD_UPLOADED` → `PD_PARTIAL`, если из N уникальных строк реестра этапа загружено меньше N), счётчики загружено/ожидается в Приложении 2 и в API процесса. `upload_scenario` считает `*_PARTIAL` загруженным этапом, а `checks` из `completeness` не вычисляются. Найден и исправлен один край: если у этапа есть файлы, но ни один не совпал со строкой реестра (например, файл, загруженный вручную рядом с пакетом), статус был бы `*_MISSING`, хотя раньше был `*_UPLOADED`; теперь `*_PARTIAL` (`v3_pipeline.document_completeness`). Без реестра в пакете поведение прежнее.

**DOCX.** Текст основного WordprocessingML (до 6000 знаков) сохраняется как `SourceFragment` (`source_system="docx"`, без bbox) только при загрузке файла через интерфейс/API. Пакетный путь и CLI DOCX не читают (`batch_package` исключает не-PDF как `UNSUPPORTED_EXTENSION`), поэтому для CLI и batch-run опция ничего не меняет. Что может измениться в интерфейсе: у DOCX-документа появляется текстовый фрагмент, и `_extract_stage_value` прогоняет по нему `default_extractors()`. Из них значение возвращает только `RegexExtractor` по `Param.regex_pattern`; у официальной матрицы 132 параметров `regex_pattern=None` (`official_dataset.py:447`), а Table/Semantic/OCR/CV возвращают `[]`. Поэтому для официальной матрицы находки из DOCX не появляются. Это проверено тестом `test_official_matrix_extracts_nothing_from_docx_text` (ни один параметр официальной матрицы не имеет шаблона; ни один экстрактор ничего не вернул на тексте с «площадь/ширина/EI»). Если администратор добавит параметр с `regex_pattern`, DOCX-текст начнёт давать значения: на демо-матрице (5 параметров с шаблонами, используется только синтетическим набором) это наблюдалось: после добавления DOCX-фрагмента группы доказательств изменились, поэтому тест выражен структурно, а не сравнением прогонов.

**Планировщик отчёта ML.** Запускается только из startup-хука `app.main` (процесс uvicorn, один процесс в образе: `CMD uvicorn app.main:app` без `--workers`). CLI и `worker_case10` не импортируют `app.main` (тест запускает отдельный интерпретатор и проверяет `sys.modules`). `TestClient(app)` без контекста startup не вызывает, поэтому в тестах планировщик не стартует. Повторный вызов startup не создаёт вторую задачу. Что добавлено: пауза 30 с перед первым тиком (не конкурирует со стартом и healthcheck); файл блокировки `/data/reports/.weekly_scheduler.lock` (создание `O_EXCL`, блокировка старше 15 минут считается брошенной), чтобы два API-процесса не писали отчёт одновременно; прежний файловый маркер интервала `.weekly_scheduler_state.json` сохранён (перезапуск контейнера не повторяет отчёт). Сети нет; на пустой БД сохраняется один отчёт «данных мало» (тест). Ошибка тика логируется и не валит процесс.

Честное ограничение: DOCX-опция и планировщик в CLI-прогонах не участвуют по построению, поэтому идентичность для них тривиальна; содержательное доказательство для DOCX — структурное (см. выше), для планировщика — тесты процесса.
