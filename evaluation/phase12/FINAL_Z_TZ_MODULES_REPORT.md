## 3. Еженедельный отчёт ML (модуль 10)

**Файлы:** `api_service/app/domain/ml_weekly_report.py` (новый), endpoint `GET /api/case10/ml/reports/weekly?end=&project_id=&format=json|html` (роль ML_ENGINEER или администратор; иначе 403), команда `weekly-report` в `cli.py`, `frontend_react/src/components/MlReport.jsx` (вкладка видна только этим ролям).

Содержимое: окно из семи дней, оканчивающееся датой `end` (по умолчанию сегодня, UTC), и предыдущее окно; решения инспекторов (подтверждено / отклонено / уточнение) в целом, **по разделам Матрицы** и **по методам** (источник находки или метод гипотезы), доля подтверждённых по решениям с интервалом Уилсона 95 %, изменение к прошлой неделе (число решений и доля), **топ причин отклонения** по `reason_code`, проверки свободных гипотез, сведения из `ml_retraining_logs` (последние пять) и состояние журнала отклонений. Определения чисел записаны в самом отчёте (`definitions`).

**Рекомендации — шесть фиксированных правил** (`RECOMMENDATION_RULES`), каждое называет цель и числа, на которых стоит: метод отклонён более чем в 60 % решений при ≥ 10 решений («метод X отклонён > 60 % → пересмотреть порог»); то же для раздела; одна причина — не менее 40 % отклонений (≥ 10) с советом по причине; падение доли подтверждённых на 15 п. п. и более (≥ 10 решений в обе недели); уточнения > 30 %; последний релиз переобучения заблокирован шлюзом.
**Честность при малых данных:** меньше 20 решений за неделю → `data_sufficiency.enough = false`, текст «Данных мало…», рекомендации не формируются, числа и интервалы показываются; пустая история не падает (проверено API и CLI на пустой базе).

## 7. Hardening контейнеров

`docker-compose.case10.hardened.yml` — **необязательный** второй файл (`-f docker-compose.case10.yml -f docker-compose.case10.hardened.yml`), основной стенд не менялся, чтобы не рисковать запуском. Для api, worker, gateway, UI: `no-new-privileges`, `cap_drop: ALL` (nginx получает обратно CHOWN, SETGID, SETUID, NET_BIND_SERVICE), `read_only: true` + tmpfs для `/tmp` (UI — ещё `/var/cache/nginx`, `/var/run`); шлюз работает от пользователя `node` образа.

**Проверено (на образах `case10-api|gateway|ui:latest` от 29.09, не на образе из текущего дерева):** `docker compose config` — чисто; полный стенд из пяти контейнеров поднят под отдельным именем проекта `case10hardz` на нестандартных портах и удалён (`down -v`): api healthy (`/health`), RabbitMQ, worker, шлюз и UI запущены, UI отвечает 200, вход администратором по API, загрузка двух PDF напрямую в API принята; в логах worker нет ошибок записи; контейнер api: запись в `/app` запрещена, в `/data` разрешена; `python -m app.cli run` на пакете из трёх файлов под `--network none --read-only --cap-drop ALL` дал `result.json` (132 проверки).
**Замечания:** (1) в режиме `read_only` CLI-запуск без смонтированного `/data` падает на создании каталога данных — для `docker run` нужны `-e API_DATA_DIR=… -e API_LOG_DIR=…` на записываемый том (записано в шапке файла); в стенде `/data` — том. (2) Загрузка файла **через старый образ шлюза** (curl, multipart) отвечает «fetch failed» и **без** hardening — не связано с этой правкой; образ шлюза будет пересобран шагом E1, повторить загрузку через UI там.
**Не сделано:** запуск api/worker **не от root** — модель эмбеддингов лежит в `/root/.cache` образа, непривилегированный пользователь её не прочтёт; нужны правка Dockerfile (`HF_HOME` вне `/root`, `USER`, `chown /data /logs`) и пересборка образа — это за рамками шага (образ не пересобирается); rabbitmq не трогался.
