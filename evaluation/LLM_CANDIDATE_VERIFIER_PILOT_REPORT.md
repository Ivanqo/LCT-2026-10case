# Компактная LLM как верификатор кандидатов (Промпт 9.2): пилот и решение

Дата: 2026-09-24. Продолжение Промпта 9.1 (`CASE10_TZ_COMPLIANCE_AUDIT.md`, «Часть 0»): три детерминированных
фикса ранжирования для LOS3A PZ-001/002/004, из которых безусловно сработал только PZ-004.
Здесь проверено, может ли компактная open-weights LLM **выбирать среди уже найденных
кандидатов** (никогда не генерируя значение) лучше, чем `pick_best_candidate`.

**Итог: ПРИНЯТЬ как опциональный шаг, выключенный по умолчанию; при включении — режим
`shadow` по умолчанию, `rerank` — только осознанно.** На 101 реальном пуле кандидатов с
6 новых объектов верификатор статистически значимо лучше baseline в парном сравнении
(0.525 против 0.386, McNemar exact p = 0.0094), на всех трёх названных случаях выбирает
верного PD-кандидата, но у него есть три задокументированных ограничения, из-за которых
он **не** заменяет детерминированный выбор по умолчанию: сильное позиционное смещение,
низкая точность на пулах без правильного кандидата и то, что латентность на H100 не
измерена (раздел 6).

## 1. Модель и окружение

| | |
|---|---|
| Модель | `Qwen/Qwen3-4B-Instruct-2507` (Apache-2.0, instruct без "thinking", хороший русский) |
| Локально (RTX 4050 Laptop, 6 ГБ) | 4-bit NF4 (bitsandbytes): веса 2.65 ГБ; пик выделения 7.29 ГБ → WDDM выгружал в shared memory |
| Сервер проверки (H100 80 ГБ) | bf16 ≈ 8 ГБ весов — помещается в долю процесса `CASE10_GPU_MEMORY_FRACTION=0.2` (16 ГБ). **Не измерено**, это расчёт |
| Окружение пилота | изолированный venv `E:\case10_llm_pilot` (torch 2.5.1+cu124, transformers 4.57.6) — torch в `venv` проекта только CPU |
| Код | production-модуль `api_service/app/domain/llm_candidate_verifier.py` загружался в пилоте **напрямую по пути**: тот же промпт, тот же парсер, тот же backend, что и в приложении |

Промпт (`SYSTEM_PROMPT`) написан **до** просмотра каких-либо ответов модели и **не менялся**
по ходу пилота: цифры ниже не результат подгонки промпта под эти 101 пул.

## 2. Данные и разметка

- **Пулы кандидатов.** Реальный `run_process` (полный официальный каталог 132 параметров,
  live-тэггер, in-memory sqlite, реальные PDF с `E:\`) на всех 6 новых объектах; перехвачен
  **каждый** вызов `pick_best_candidate` вместе с выбором baseline
  (`llm_verifier_pilot/capture_candidate_pools.py`). Прогон воспроизвёл прошлую сессию
  один в один: LOS3A 451 фрагмент / 10 comparable, ALT79B 381/3, POL17 319/5, DOO25 119/1,
  OKT103 271/0, IZM12 216/0 — 19 comparable-групп. Итого **101 пул** (numeric 68, enum 26,
  compound 7), в том числе все PD/RD-пулы 19 comparable-групп. Верификатор получает пул
  в том порядке, в каком его видел `pick_best_candidate` (включая кандидатов, которых
  потом отсёк семантический порог), максимум 10 кандидатов.
- **Ручная разметка** (`llm_verifier_pilot/labels_*.json`), по методике
  `case10_silver_review_pass1`: каждого кандидата я разметил по его строке и окружающим
  визуальным строкам **до** первого запуска модели (временные метки файлов: разметка
  23:14–23:30, первый вызов LLM после 23:40). `strict` — строка однозначно является
  значением именно этого параметра и извлечено именно её значение; `lenient` — плюс
  защитимые альтернативные определения; `[]` — правильного кандидата в пуле нет
  (правильный ответ — «ни один»). Правило оценки одинаково для обеих систем: верно, если
  выбор ∈ `strict`, либо `strict` пуст и система воздержалась.
- **Ограничение разметки:** один разметчик (агент, писавший и промпт), по тексту строк без
  повторного открытия PDF для каждого из ~600 кандидатов. Это SILVER, а не GOLD.

## 3. Результаты (прямой порядок кандидатов, n = 101)

| Срез | baseline `pick_best_candidate` | LLM-верификатор | парное сравнение |
|---|---|---|---|
| **Все пулы (strict)** | 39/101 = **0.386** [0.297, 0.484] | 53/101 = **0.525** [0.428, 0.619] | проиграно 6, выиграно 20, **p = 0.0094** |
| Все пулы (lenient) | 41/101 = 0.406 [0.315, 0.503] | 59/101 = 0.584 [0.487, 0.675] | 5 / 23, p = 0.0009 |
| Правильный кандидат есть (n=45) | 29/45 = 0.644 [0.498, 0.768] | 38/45 = 0.844 [0.712, 0.923] | 1 / 10, p = 0.012 |
| Правильного кандидата нет (n=56) | 10/56 = 0.179 [0.100, 0.298] | 15/56 = 0.268 [0.170, 0.396] | 5 / 10, p = 0.30 |
| Пулы с ≥2 кандидатами (n=85) | 31/85 = 0.365 | 45/85 = 0.529 | 4 / 18, p = 0.0043 |
| Только numeric (n=68) | 17/68 = 0.250 | 31/68 = 0.456 | 3 / 17, p = 0.0026 |

95% ДИ — Wilson; p — точный McNemar по несогласным парам (правильный тест для **парных**
данных: обе системы решают одни и те же 101 пул). Интервалы для всех пулов перекрываются
лишь краем (0.428 против 0.484); по парному критерию разница значима.

Ответ неразбираем (не JSON / индекс вне диапазона): 1/101 — такой ответ считается
«нет сигнала», а не выбором.

### 3.1. Три названных случая LOS3A (критерий успеха из задачи)

| Случай | baseline | LLM | Верно |
|---|---|---|---|
| PZ-001 PD | 4,5 (порог высоты консоли, реверс строк) | **1076,49** (ТЭП ПБ.1 стр. 9) | 1076,49 |
| PZ-002 PD | 16867,90 («площадь помещений» по СП 118) | **25036,27** («Площадь здания по СП 54.13330.2016») | 25036,27 |
| PZ-004 PD | 88264,00 | 88264,00 | 88264,00 |
| PZ-001 RD | — (семантический порог отсёк все 4 верных кандидата) | 1076,49 | 1076,49 |
| PZ-002 RD | 25036,27 | **23724,45** («Общая площадь здания» в таблице раздела ТМ) | 25036,27 (23724,45 допустимо только в lenient) |
| PZ-004 RD | 88264,00 | 88264,00 | 88264,00 |

Верификатор решает оба случая, где эвристика ошиблась (PZ-001, PZ-002 на PD), и не ломает
PZ-004 — **без** заполненного `sp_reference`, от которого зависит «спящий» фикс PZ-002 из
Промпта 9.1. Но на RD PZ-002 он же вносит регрессию.

### 3.2. Сквозная проверка внутри production pipeline (LOS3A, rerank)

`llm_verifier_pilot/e2e_los3a_verifier.py`: реальный `run_process`, верификатор вызывается
из `cross_stage_localization.resolve_stage_round` без всякого кода харнесса:

- **PZ-002: PD = RD = 25036,27 → NEGATIVE_VERIFIED** (без верификатора: ложное расхождение
  16867,90 против 25036,27). PZ-004 без изменений (верно).
- **Первый запуск нашёл реальный интеграционный дефект:** `gpu.py` ограничивает процесс
  долей `CASE10_GPU_MEMORY_FRACTION=0.2`; на 6-ГБ карте это 1.2 ГБ — модель упала с OOM при
  загрузке, верификатор (как и задумано) деградировал до no-op, pipeline не упал.
  Исправлено: `choose_precision` считает от **разрешённой** доли, а не от полного объёма
  карты, и отказывается загружать модель, если не влезает даже 4-bit.
- Во втором запуске (доля поднята до 0.95) длинные промпты (~3000 токенов, 10 кандидатов)
  всё равно получали OOM: в процессе pipeline модель делит память с семантической моделью,
  а выгрузки в shared memory больше нет. Эти вызовы деградировали до no-op — поэтому RD у
  PZ-002 остался верным отчасти **случайно** (в изолированном прогоне модель выбрала там
  23724,45), а PZ-005/006/008 вердикта не получили. Это ограничение 6-ГБ ноутбука; на H100
  с долей 16 ГБ запас большой, но это не измерено.

### 3.3. Побочная находка: «19 comparable-групп» в основном сравнивают неверные значения

Из 19 comparable-групп Промпта 8.1 **только в 7 все значения стадий действительно верны**
(у LLM — в 8). Например, на LOS3A PZ-005 (подземный объём) и PZ-006 (надземный) сравнивается
**общий** объём 88264,00 с самим собой → NEGATIVE_VERIFIED по неверным данным; PZ-008
сравнивает высоту **соседнего** здания из отчёта по инсоляции (10,00) с номером пункта
(2.12). Счётчик comparable-групп, приводившийся ранее как выигрыш по полноте, завышает
реальную полезность: это вопрос точности, а не наличия кандидатов.

## 4. Где верификатор ошибается

1. **Принимает мусор там, где baseline честно воздержался.** 5 из 6 регрессий — пулы, где
   семантический порог отсёк всех кандидатов, а модель выбрала: инициалы «В.Г.» как класс
   энергоэффективности, номер пункта «1» как площадь площадок и т. п. Отсюда правило
   интеграции: **верификатор не вызывается, если детерминированный выбор воздержался.**
   Эта политика (выбрана **после** просмотра регрессий, поэтому это исследовательский,
   а не заранее зафиксированный результат) даёт 56/101 = 0.554, проиграно 1 / выиграно 18,
   p = 0.0001.
2. **Низкая точность на пулах без правильного кандидата**: воздерживается лишь в 15 из 56.
   Точность ненулевого выбора — 38/86 = 0.44 (у baseline 29/89 = 0.33).
3. **Сильное позиционное смещение.** Повторный прогон с обратным порядком кандидатов на
   первых 42 пулах с ≥2 кандидатами (полный обратный проход не завершён из-за
   латентности, см. раздел 5): точность та же (24/42 в обе стороны), но **выбранное значение
   меняется в 19 из 42 пулов**, а показанного первым модель выбирает в 19/42 (прямой) и
   18/42 (обратный) случаев. Аггрегированная точность устойчива, отдельный вердикт — нет.
   Главная причина не включать `rerank` по умолчанию.
4. Выбор кандидата, у которого верное число есть в **контексте**, но извлечено другое
   (LOS3A AR-041: взято «0,000», обоснование ссылается на соседние «1,05 м») — правило 3
   промпта это запрещает, модель 4B ему не всегда следует.

## 5. Латентность

Один вызов на **пул** (параметр × стадия), а не на кандидата: 7–26 пулов на объект в этом
пилоте (не «тысячи кандидатов»). На RTX 4050, 4-bit: среднее 26.5 с, p50 17.2 с,
p90 48.3 с, максимум 123 с; промпт в среднем 1549 токенов (макс. 3164). Длинные промпты
медленные из-за выгрузки VRAM в shared memory (пик 7.29 ГБ при 6 ГБ физических). E2E LOS3A
с верификатором: 589 с против 461 с без него. **На H100 (bf16) не измерено** — ожидается
на порядок быстрее, но это не утверждение, а гипотеза для следующего шага.

## 6. Решение и встраивание

- `CASE10_LLM_VERIFIER_ENABLED=0` по умолчанию (как `CASE10_SEMANTIC_ANCHOR_FALLBACK_ENABLED`
  в checkpoint 41). При выключенном флаге нет ни вычислений, ни изменений: `delta` групп
  байт-в-байт прежний (покрыто тестами).
- `CASE10_LLM_VERIFIER_MODE=shadow` по умолчанию: выбор не меняется, вердикт (выбранный
  документ/страница/значение, согласие с детерминированным выбором, обоснование, латентность)
  кладётся в `EvidenceGroup.delta["llm_verification"][stage]` для evidence-карточки
  инспектора. Статус остаётся CANDIDATE до решения инспектора, как и раньше.
- `rerank` — вердикт заменяет выбор, «ни один» → стадия воздерживается. Включать только
  после подтверждения на отложенной выборке (раздел 7).
- В обоих режимах: не вызывается, если детерминированный выбор воздержался; неразбираемый
  ответ или ошибка/OOM → no-op; значение PD **никогда** не показывается модели при проверке
  RD/ID (иначе она «подтягивалась» бы к согласию и прятала бы именно те расхождения, ради
  которых существует система).
- Код: `llm_candidate_verifier.py` (промпт, строгий парсер, `review_pick`,
  `choose_precision`), `cross_stage_localization.resolve_stage_round` (сигнал 5),
  поле `llm_verification` в 4 классах Observation, `official_evidence._with_llm_verification`.
  Тесты: `test_case10_llm_candidate_verifier.py` (33 новых). Полный набор: **503/503** (было 470).
- Docker-образ: зависимости (`transformers`, `accelerate`, `bitsandbytes`) и веса модели
  **не** добавлены в образ этой сессией — при выключенном флаге они не нужны, и
  `_load()` без них корректно деградирует. Добавить их нужно вместе с проверкой на H100.

## 7. Что осталось открытым

1. **Отложенная выборка**, размеченная не тем, кто писал промпт: подтвердить пост-hoc
   политику «не отменять воздержание» и только потом рассматривать `rerank`.
2. **Замер на H100** (bf16, доля 0.2) — латентность и отсутствие OOM на длинных промптах.
3. **Позиционное смещение**: проверить голосование по двум порядкам или сортировку
   кандидатов по признаку, не связанному с рангом; завершить обратный проход на всех 85 пулах.
4. Самая большая доля ошибок baseline — **неверно извлечённое значение на правильной строке**
   (номер пункта, значение соседней колонки). Это задача извлечения, а не выбора кандидата;
   верификатор её не решает, а лишь может отказаться от такого кандидата.
