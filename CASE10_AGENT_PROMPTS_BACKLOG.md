## 0. Что изменилось: новые факты (экспертная сессия + комплект 1.1)

1. **Как оценивают.** 75% — техническая часть: функциональная полнота, OCR/извлечение, выявление несоответствий (precision/recall/F1). 25% — питч и **живое демо** (настоящий прогон документов, а не макеты). Точная формула не раскрыта. 100-балльная формула с ограничением «59» — архивный пилот организатора. Ориентир — метрики ТЗ 14.3 и листа «МЕТРИКИ» матрицы 1.1.
2. **ПД — эталон.** Нужен consistency checker ПД ↔ РД ↔ ИД, а **не** проверка ПД на СНиП/СП/СанПиН. Правила вида «если этажей > 10 — лифт» — не основная логика.
3. **Скрытый тест — другая документация.** Речников (`test_hidden_organizer`) — архив, а не финальный тест. Всеми материалами из папки можно пользоваться для разработки (вопросы Q11, Q13). Хардкод под известные файлы, страницы и кейсы запрещён по смыслу («нельзя подгонять под выданные PDF»). Какие из 132 параметров попадут в тест — неизвестно, нужна расширяемая матрица правил.
4. **Матрица 1.1**: содержание 132 параметров совпадает с нашим каталогом (названия, триггеры, источники — проверено), но коды — **M-001…M-132**. Вместо «Критическое (приостановка работ)» теперь «приоритет экспертной проверки HIGH/MEDIUM» (106/26) — это только очерёдность проверки, не юридический статус.
5. **Реестр файлов обязателен** (Перечень ИД 1.1): каждый пакет сопровождается CSV/XLSX/JSON с полями `object_id, file_id/file_name/SHA-256, doc_stage, discipline, document_code, revision, approval_status (DRAFT/APPROVED/FOR_CONSTRUCTION/SUPERSEDED/CANCELLED), approval_date, sheet_page_range, predecessor_id/successor_id, signature_status`. Без реестра пакет принимается со статусом `CLARIFICATION_REQUIRED`. Правила выбора источника: одна утверждённая редакция → её; явная замена → старую исключить; несколько без статуса → `CLARIFICATION_REQUIRED`, вывод блокируется; нет документа → `MISSING_EVIDENCE`; неприменим → `NOT_APPLICABLE` с основанием; нечитаем → `NOT_COMPARABLE`.
6. **Метрики 1.1**: P/R/F1 по evidence_group («правильный параметр/тип расхождения + корректное доказательство»). **«Без полного доказательства finding не засчитывается»**: file_id + страница + bbox с IoU ≥ 0,50 после учёта CropBox/MediaBox/Rotate. FPR считается на `NEGATIVE_VERIFIED` **и на устаревших редакциях**. Связка документов — точные object_id + стадия + шифр + актуальная редакция; конфликты редакций есть в скрытом тесте.
7. **Официальные примеры нарушений** — это не скалярные ТЭП:
   - экспликации и спецификации помещений и квартир — ALT79B, DOO25, POL16, SOSH25, частично LOS3A;
   - состав кровли плюс лист изменений РД («бронированный лист … исключён») — UNDMS;
   - перенос двери, записанный в ведомости изменений, — LOS3A;
   - ИД: схема ремонта свай — IZM12; превышение допусков — OKT103;
   - Тюмень: ветви вытяжки и контуры тёплого пола **по помещениям**.

   Почти всё это лежит **в текстовом слое** PDF. Полярная 17 — отрицательная пара, контроль FP.
8. **Поля индексных файлов организатора** (`annotations.jsonl`, `files_index` и т.п.) на inference могут быть недоступны — письменный ответ ещё не пришёл. Проектировать так, будто их нет.
9. **Модели — только локальные**, с открытыми весами и подходящей лицензией, с разумными ресурсами; квантование приветствуется. Облачные API в критическом пути недопустимы. Нельзя быть «чёрным ящиком»: каждое значение должно быть видно в первоисточнике.
10. **Инспектор** (что эксперты описали явно):
    - единое окно с синхронными панелями ПД/РД/ИД;
    - карточка доказательства как центральная сущность;
    - около 3 осознанных действий на решение;
    - выбор редакции с обоснованием;
    - добавление, удаление и уточнение фрагментов доказательств — с версиями и историей; исходные файлы, OCR и машинный вывод не перезаписываются;
    - групповые операции только для однотипных кандидатов, осторожно с массовым отклонением;
    - комплектность — против **ожидаемого манифеста**, а не по числу файлов;
    - `low_quality` вместо выдумывания.
11. **Лимиты 50/200 МБ — только для UI.** Большие массивы (гигабайты) приходят серверным или интеграционным путём.
12. **Сдача — два комплекта.** Технический: код, контейнер, воспроизводимый запуск, API, пример JSON, веса, документация, желательно рабочий стенд. Демо: питч, живое демо, видео. Официальный скрипт метрик и JSON-валидатор, вероятно, опубликуют.
13. **Не тратить время** до готовности ядра: DWG-парсер, SSO/IAM, промышленный CI/CD, нагрузка на 100 пользователей, реальная УКЭП, антивирус, десятки экранов, нормоконтроль, облачные AI API.

## Фаза 12 — «Ядро 1.1» (25–29.09)

### Общий контекст Фазы 12 (читать первым; все промпты ссылаются сюда)

**Цель.** Локальный, воспроизводимый, объяснимый сервис: извлечь утверждённое значение или решение из ПД → найти соответствующее в РД/ИД → обнаружить расхождение → показать доказательство → решение инспектора → протокол → API/JSON (конспект, §3, §39.7, §42). Каждая находка — evidence_group с кодом M-xxx, location, значениями ПД/РД/ИД и **полным доказательством** (file_id, SHA-256, стадия, шифр, редакция, статус утверждения, страница, bbox в [0;1], confidence).

**Целевая функция.** `evaluation/grader_sim.py` (строит P0) по метрикам 14.3 / матрицы 1.1 на наборах:
- **(A) официальные метки:**
  - `public_train_checks.jsonl` — 10 положительных строк Тюмени;
  - строки `TRAIN_PUBLIC` из `all_gold_checks.jsonl` — 5 отрицательных Новослободской;
  - 4 проверки Речникова — архив, использование разрешено;
  - 9 кейсов комплекта предметной разметки (`case_data/extracted/02_gold_methodology/domain_violation_reannotation_20260817/annotations.jsonl`: страницы и прямоугольники);
- **(B)** те же объекты в **живом режиме** — разметка организатора отключена: основной сценарий скрытого теста;
- **(C)** SILVER-корпус стенда A и метки 9.3;
- **(D)** посевы L1/L2 стенда A.

Улучшение засчитывается, только если видно в grader_sim, прежде всего на (B).

**Правила данных.** Всё из папки организатора можно использовать для разработки. Но механизмы — общие: никаких имён файлов, номеров страниц, диапазонов номеров помещений или объектных констант в коде. Каждый механизм проверяется на **объекте, не использованном при его разработке**; какой объект был dev, а какой проверочный — фиксировать в отчёте. Значения из gold никогда не используются как lookup. SILVER не попадает в `training_release.py`.

**Среда и ограничения.**
- Только локальные модели с открытыми весами и совместимой лицензией (лицензию записать); в рантайме никаких внешних API.
- Время по ТЗ §11: сравнение 132 параметров ≤2 мин, OCR ≤3 мин/100 стр., протокол ≤30 с, CV ≤30 с/чертёж, API p95 ≤200 мс. Новый механизм — не больше +30–60 с на объект на 24 ядрах. Лимиты — детерминированные (документы, страницы, клипы), не по часам; байт-детерминизм submission (E1) сохранять.

**Параллельная работа.**

- Чужие файлы — только чтение; нужна правка чужого файла — записать в отчёт, решает I.

## Общие правила

Все материалы из папки организатора можно использовать для разработки (экспертная сессия, Q11). Скрытый тест — другая документация (Q13). Запрещено: значения gold как lookup в inference-коде; имена файлов, страницы, диапазоны номеров и объектные константы в механизмах; выдача низконадёжного вывода как факта (`LOW_QUALITY` / `CLARIFICATION_REQUIRED` вместо догадки); внешние сервисы в рантайме. SILVER-данные и `multi_object_annotation_20260817` с `training_release.py` и официальными train/gold не смешивать без экспертного ревью. Каждый вывод системы должен быть проверяем инспектором за секунды по первоисточнику.
